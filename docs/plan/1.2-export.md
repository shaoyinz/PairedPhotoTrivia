# 1.2 Export

Two paths, one CSV schema, so the Python side has a single reader either way:

```
asset_id,utc_epoch,tz_offset_s,lat,lon,is_screenshot,burst_id,is_burst_pick,
camera_make,camera_model,width,height
```

`asset_id` is a local identifier only — it never leaves the device in phase 2, and in the spike
it exists so a detected trip can be traced back to real photos while hand-checking. Empty
`lat`/`lon` means no GPS, which is a measurement, not a defect: it feeds the coverage report.

## 1.2a iOS exporter — primary path (`ios/MetadataExport/`)

A deliberately small SwiftUI app each partner runs on their own iPhone. One screen, one button,
one share sheet.

**Status (2026-10-02):** built — `xcodebuild` for `generic/platform=iOS` succeeds with no
warnings (Swift 6, iOS 16+). Ran end to end in the iOS 27.0 simulator on its 6 stock photos:
the header matches the pinned schema, the 3 "differs from this phone's" rows are exactly the
Iceland photos (simulator on Pacific time), and no row fell back to the phone's zone, so
`localCreationDate` still resolves on iOS 27. The on-device check below is the one open item.
Build and run steps: [`ios/README.md`](../../ios/README.md).

- [x] Request `PHPhotoLibrary` read authorization, handling `.limited` (ask for full access
      here; a limited selection makes coverage numbers meaningless, and the real app needs the
      limited path tested anyway — note the behavior for phase 2). *Limited still exports, but
      the screen warns, links to Settings, and the file is named `…_LIMITED.csv` so it cannot
      pass for a full export on the Mac.*
- [x] Enumerate `PHAsset` with `PHFetchOptions`, `mediaType == .image`, no sorting. *Fetch
      defaults kept: no hidden assets, one asset per burst (Photos' own count). Source types set
      to user library + iTunes-synced, so shared albums — other people's photos — stay out.*
- [x] Per asset: `localIdentifier`, `creationDate` → UTC epoch, the asset's
      timezone offset for local-hour reasoning ([§1.5](1.5-anchors.md)), `location?.coordinate`,
      `mediaSubtypes.contains(.photoScreenshot)`, `burstIdentifier`,
      `representsBurst`, `pixelWidth`/`pixelHeight`. *PhotoKit has **no public per-asset time
      zone** (checked against the iOS 27 SDK headers). The exporter reads PHAsset's private
      `localCreationDate` (the capture instant shifted by the photo's own offset) and falls back
      to the phone's time zone when it is missing or not a whole quarter hour. Fine for a
      sideload; phase 2 cannot ship it. The screen counts both the fallbacks and the photos whose
      zone differs from the phone's — the second number is how wrong phase 2 would be with the
      phone's zone.*
- [x] Camera make/model via `PHAssetResource` / `CGImageSource` metadata — only if it is cheap;
      it is used to split coverage by camera-vs-imported, so drop the column rather than make
      the export slow. *Not cheap: make/model exist only in EXIF, which means fetching image data
      (downloading iCloud-only originals). Dropped by leaving both cells empty, not by changing
      the pinned schema. Empty here means unknown, not imported (see [§1.8](1.8-evaluation.md)).*
- [x] Stream rows to a CSV in the app's temp directory; show a progress count (expect tens of
      thousands of assets). *500-row chunks, each in its own autorelease pool; screen kept awake
      while exporting.*
- [x] Export via share sheet (AirDrop to the Mac). Never fetch image data — metadata only, so
      the app works with photos that live only in iCloud
- [ ] Build check: run on device, confirm the row count matches Photos' own album count. Also
      read the time-zone lines on the finished screen: "differs from this phone's" should be
      roughly the photos taken while traveling. If it is close to the total row count,
      `localCreationDate` does not mean what we think — the rows are written but `tz_offset_s` is
      wrong, so stop before §1.5

Known risk for matching, not fixable here: a couple sharing an **iCloud Shared Photo Library**
both export every shared photo, whoever took it, so a solo trip moved into the shared library
looks like a trip together. PhotoKit has no public contributor field, so ask whether a test
couple uses one before trusting their matches.

Distribution: a free personal team sideload from Xcode works and expires after 7 days, which is
fine for a one-time export. A remote partner needs TestFlight, or a screen-share walkthrough of
the Xcode build on their own Mac if they have one.

## 1.2b osxphotos — alternative where a synced Mac library exists

- [ ] `photoquiz ingest --person a --library <path> --out data/a_photos.parquet`, pulling
      `uuid`, `date`, `tzoffset`, `latitude`, `longitude`, `screenshot`/`uti`, `burst`,
      `burst_selected`, `original_filename`, `exif.camera_make`/`model`, `width`, `height`
- [ ] Emits the same CSV schema as 1.2a, so the two paths are interchangeable
- [ ] Requires iCloud Photos enabled on that Mac and Full Disk Access for the terminal.
      Metadata syncs in full even with "Optimize Mac Storage" on; the spike never needs
      original pixels
